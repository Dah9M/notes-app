# Отчёт: Notes App

## 1. Доменная область

Приложение для ведения личных заметок (Notes App). Каждый пользователь регистрируется, входит в систему и работает со своим приватным набором заметок: создаёт, читает, редактирует и удаляет их, а также организует заметки с помощью тегов и фильтрует список по тегу. Заметки одного пользователя не видны другим пользователям.

## 2. Стек реализации

| Слой | Технологии |
|---|---|
| Backend | Java 21, Spring Boot 3.3.5 (Spring Web, Spring Data JPA) |
| БД | PostgreSQL 16 |
| Миграции БД | Liquibase — запускается отдельным одноразовым контейнером (`liquibase/liquibase`), не встроен в backend |
| Frontend | HTML5, CSS3, vanilla JavaScript (без фреймворков и сборки) |
| Взаимодействие | HTTP/REST (JSON), фронтенд обращается к backend напрямую через `fetch` |
| Инфраструктура | Docker, Docker Compose (4 независимых процесса: postgres, migrate, backend, frontend) |

Аутентификация реализована максимально упрощённо и осознанно: без токенов, сессий и хеширования паролей — логин/пароль сверяются напрямую в БД, а личность пользователя на последующих запросах передаётся заголовком `X-User-Id`. Это сознательное решение: задание курса SRE, а не курса по безопасности, и усложнение авторизации не добавляет ценности для последующих ДЗ (логи, метрики, балансировка), а только увеличивает объём кода.

## 3. Основные сущности

- **User** — id, username (уникальный), password, createdAt
- **Note** — id, title, content, owner (User), tags (Tag, многие-ко-многим), createdAt, updatedAt
- **Tag** — id, name (уникальный)

CRUD полностью реализован для **Note** и **Tag** (`/api/notes`, `/api/tags`). Для **User** — регистрация и вход (`/api/auth/register`, `/api/auth/login`), т.к. пользователь не является объектом самостоятельного управления в рамках предметной области приложения.

## 4. Соответствие методологии «Приложение 12 факторов»

Ниже — разбор по названиям и критериям **ровно в той формулировке, что дана в презентации курса** («Введение в курс. 12 факторов», Искандер Мусин, T-Bank Statist). Для каждого фактора: определение из презентации → критерий «как правильно» → почему он выполнен в проекте, с конкретным доказательством.

---

### Фактор 1. Кодовая база (Codebase)
*Одна кодовая база в системе контроля версий, много развёртываний*

**Как правильно (по презентации):** один репозиторий на приложение, система контроля версий, каждый контур — из одной кодовой базы.

**Статус: ✅ Выполнено.** Один git-репозиторий (`notes-app`, https://github.com/Dah9M/notes-app), папки `backend/` и `frontend/` — части одного кодбейза. Любое окружение (локальное, тестовое, будущий прод) разворачивается из одного и того же репозитория без форков и копий кода.

---

### Фактор 2. Зависимости (Dependencies)
*Явно объявляйте и изолируйте зависимости*

**Как правильно:** манифест зависимостей, явная фиксация версий, изоляция окружений, исключение неявных зависимостей.

**Статус: ✅ Выполнено.**
- Backend: манифест — `pom.xml`, все версии зафиксированы явно (родитель `spring-boot-starter-parent:3.3.5`, `lombok.version=1.18.42` и т.д.).
- Все Docker-образы пинятся по тегу, а не `latest`: `maven:3.9-eclipse-temurin-21`, `eclipse-temurin:21-jre-alpine`, `postgres:16-alpine`, `python:3.12-alpine`, `liquibase/liquibase:4.27`.
- Сборка полностью изолирована в контейнере (multi-stage Dockerfile) — ничего не берётся «из системы» хост-машины.
- Frontend — vanilla JS без единой внешней библиотеки: неявных зависимостей нет физически.

---

### Фактор 3. Конфигурация (Config)
*Храните конфигурацию в окружении*

**Как правильно:** всё, что меняется между окружениями — в переменных окружения; чувствительные данные — там же; код не содержит конфигурацию.

**Статус: ✅ Выполнено.** `application.yml` не содержит ни одного значения — только `${DB_URL}`, `${DB_USER}`, `${DB_PASSWORD}`, `${SERVER_PORT}`, `${FRONTEND_ORIGIN}`. Frontend — статические файлы без собственного рантайма, поэтому `API_BASE_URL` подставляется в `js/config.js` через `envsubst` при **старте контейнера** (`entrypoint.sh`), а не зашивается в код при сборке образа. Секреты и адреса — только в `.env` (не в git, есть `.env.example`-шаблон).

---

### Фактор 4. Сторонние сервисы (Backing services)
*Рассматривайте сторонние сервисы как подключаемые ресурсы*

**Как правильно:** БД/кэши/очереди — подключаемые ресурсы; нет разницы между локальным и облачным сервисом; замена — через конфигурацию, а не через код.

**Статус: ✅ Выполнено.** PostgreSQL подключается по URL, целиком заданному конфигурацией (`DB_URL`). Замена локального контейнера БД на внешний managed-Postgres не потребует изменений в коде — только в `.env`.

---

### Фактор 5. Сборка, релиз, запуск (Build, release, run)
*Строго разделяйте стадии*

**Как правильно:** Build — код → артефакт; Release — артефакт + конфигурация; Run — запуск готового релиза; релиз неизменяем и имеет идентификатор.

**Статус: ✅ Выполнено.**
- **Build**: multi-stage Dockerfile — `maven package` собирает jar в изолированном build-слое.
- **Release**: `docker-compose.yml` объединяет собранный образ с конфигурацией окружения (`.env`) и присваивает ему идентификатор — `image: notes-app-backend:${APP_VERSION:-dev}` (аналогично для frontend).
- **Run**: `docker compose up` только запускает готовый релиз, кода не меняет.

Проверено на практике: `docker compose up --build` создаёт `notes-app-backend:dev` и `notes-app-frontend:dev` — конкретные, адресуемые по тегу образы.

*Остаётся как лёгкое улучшение (не блокирует факт соответствия):* сейчас тег по умолчанию — `dev`; чтобы каждый релиз был по-настоящему уникально идентифицируем, достаточно передавать `APP_VERSION` из CI (`APP_VERSION=$(git rev-parse --short HEAD) docker compose build`) — механизм уже заложен, не хватает только автоматизации в pipeline, которой в проекте пока нет.

---

### Фактор 6. Процессы (Processes)
*Запускайте приложение как процессы без состояния*

**Как правильно:** процесс без состояния (stateless); состояние — во внешних сервисах; перезапуск процесса в любой момент без потери данных; сервис переносим между машинами.

**Статус: ✅ Выполнено.** Backend полностью stateless: нет серверных сессий, нет хранилища токенов в памяти процесса. Личность пользователя передаётся заголовком `X-User-Id` и проверяется прямым запросом к PostgreSQL на каждый вызов — состояние целиком во внешнем сервисе. Практически подтверждено (см. фактор 8): один и тот же процесс можно убить/пересоздать без потери данных, а два независимых процесса видят одно и то же состояние.

---

### Фактор 7. Привязка портов (Port binding)
*Экспортируйте сервисы через привязку портов*

**Как правильно:** приложение само является HTTP-сервером (self-contained); порт — в переменной окружения; сервис доступен другим по сети.

**Статус: ✅ Выполнено.** Backend сам поднимает встроенный Tomcat и биндится на `$SERVER_PORT` — без внешнего контейнера сервлетов. Frontend сам биндится на `$PORT` через `python -m http.server`. Ни один компонент не полагается на внешний веб-сервер общего назначения (nginx/Apache) — фронтенд и backend общаются напрямую по HTTP без прослойки-прокси.

---

### Фактор 8. Параллелизм (Concurrency)
*Масштабируйтесь с помощью модели процессов*

**Как правильно:** процесс — сущность первого класса; горизонтальное масштабирование — добавление процессов (не вертикальное — «большой машиной»); нет одного «главного» процесса, от которого всё зависит.

**Статус: ✅ Выполнено, проверено практически.** Поднят второй независимый инстанс backend'а из того же образа (`docker run notes-app-backend:dev`, отдельный порт 8082, та же сеть и БД) — без единого изменения кода или конфигурации приложения. Заметка, созданная через первый инстанс (порт 8080), немедленно доступна через второй (порт 8082):

```
POST :8080/api/notes → {"id":2, "title":"Written via instance A (8080)", ...}
GET  :8082/api/notes/2 → {"id":2, "title":"Written via instance A (8080)", ...}  # тот же объект
```

Это прямое доказательство: ни один инстанс не является «главным», расхождения состояния нет, масштабирование — это буквально добавление процессов. Постоянный запуск нескольких реплик за балансировщиком — предмет отдельного будущего ДЗ курса, но сама архитектура ничего для этого не требует менять.

---

### Фактор 9. Утилизируемость (Disposability)
*Максимальная надёжность за счёт быстрого старта и корректного завершения*

**Как правильно:** быстрый запуск — секунды; graceful shutdown по SIGTERM; устойчивость к внезапным падениям; восстановление данных после перезапуска.

**Статус: ✅ Выполнено, проверено практически.**
- Быстрый старт: `Started NotesApplication in 3.751 seconds` (лог Spring Boot).
- Graceful shutdown по SIGTERM подтверждён реальной остановкой контейнера (`docker compose stop`, который посылает SIGTERM):
```
Commencing graceful shutdown. Waiting for active requests to complete
Graceful shutdown complete
Closing JPA EntityManagerFactory...
HikariPool-1 - Shutdown completed.
```
- Восстановление без потери данных: весь стейт в Postgres (volume `pgdata`), сам процесс приложения ничего не хранит локально.

---

### Фактор 10. Паритет разработки и продакшена (Dev/prod parity)
*Держите окружения максимально похожими*

**Как правильно:** одинаковый стек, сервисы и конфигурация; разработчик сам деплоит (или это легко автоматизировано); непрерывный деплой уменьшает разрыв.

**Статус: ✅ Выполнено.** Локально через `docker-compose` поднимается тот же `postgres:16-alpine`, что предполагается использовать в любом другом окружении — никаких заменителей вроде H2/SQLite для «упрощения» разработки. Один и тот же `docker-compose up --build` работает одинаково что при первой сборке, что при повторном развёртывании — деплой полностью автоматизирован одной командой.

---

### Фактор 11. Логирование (Logs)
*Рассматривайте логи как потоки событий*

**Как правильно:** логи — поток событий в stdout; приложение не управляет файлами логов; сбор — внешними инструментами; централизованный анализ.

**Статус: ✅ Выполнено.** Ни backend, ни frontend не пишут логи в файлы — оба пишут в stdout контейнера (подтверждено во всех логах выше: стандартный вывод Spring Boot и access-лог `http.server`). Приложение не содержит ни единой настройки файлового аппендера. Сбор и маршрутизация логов — задача окружения выполнения; это ровно то, что будет настроено в следующем ДЗ курса (VictoriaLogs) поверх уже готового потока в stdout.

---

### Фактор 12. Административные задачи (Admin processes)
*Выполняйте задачи управления как одноразовые процессы*

**Как правильно:** миграции БД — одноразовые скрипты; запуск как одноразовые процессы в том же окружении; тот же код и конфигурация, что и у приложения; те же зависимости и инструменты.

**Статус: ✅ Выполнено, проверено практически.** Миграции Liquibase вынесены в отдельный сервис `migrate` в `docker-compose.yml` — тот же changelog (`db/changelog/`) и те же переменные подключения к БД, что использует backend, но запускается как независимый одноразовый процесс **до** старта приложения (`depends_on: condition: service_completed_successfully`), а не встроен в его старт:

```
migrate-1  | Running Changeset: changes/001-users.sql::001-create-users::notesapp
...
migrate-1  | Liquibase: Update has been successful. Rows affected: 5
notes-app-migrate-1 exited with code 0
backend-1  | Started NotesApplication in 3.736 seconds   # стартует уже на готовой схеме
```

Backend больше не содержит зависимости `liquibase-core` и не умеет сам себе накатывать миграции — это ровно паттерн «одноразовый административный процесс», а не побочный эффект старта приложения.

**Все 12 факторов выполнены**, из них 4 (Параллелизм, Утилизируемость, Административные задачи, Сборка/релиз/запуск) — не просто задекларированы, а подтверждены практическими проверками в рамках этой сессии (реальный второй процесс с общим состоянием, реальный SIGTERM с graceful-логами, реальный отдельный migrate-процесс с exit code 0, реальные тегированные образы). ## Запуск проекта

```bash
cp .env.example .env
docker compose up --build
```

- Frontend: http://localhost:8081
- Backend: http://localhost:8080

Миграции применяются автоматически как отдельный шаг (`migrate`) перед стартом backend'а.
