# Отчёт: Notes App

## 1. Доменная область

Приложение для ведения личных заметок (Notes App). Каждый пользователь регистрируется, входит в систему и работает со своим приватным набором заметок: создаёт, читает, редактирует и удаляет их, а также организует заметки с помощью тегов и фильтрует список по тегу.

## 2. Стек реализации

| Слой           | Технологии                                                                            |
|----------------|---------------------------------------------------------------------------------------|
| Backend        | Java 21, Spring Boot 3.3.5 (Spring Web, Spring Data JPA)                              |
| БД             | PostgreSQL 16                                                                         |
| Миграции БД    | Liquibase — запускается отдельным одноразовым контейнером (`liquibase/liquibase`)     |
| Frontend       | HTML5, CSS3, vanilla JavaScript (без фреймворков и сборки)                            |
| Взаимодействие | HTTP/REST (JSON), фронтенд обращается к backend напрямую через `fetch`                |
| Инфраструктура | Docker, Docker Compose (4 независимых процесса: postgres, migrate, backend, frontend) |

## 3. Основные сущности

- **User** — id, username (уникальный), password, createdAt
- **Note** — id, title, content, owner (User), tags (Tag, многие-ко-многим), createdAt, updatedAt
- **Tag** — id, name (уникальный)

CRUD полностью реализован для **Note** и **Tag** (`/api/notes`, `/api/tags`). Для **User** — регистрация и вход (`/api/auth/register`, `/api/auth/login`)

## 4. Соответствие 12 факторам


### Кодовая база
*Одна кодовая база в системе контроля версий, много развёртываний*

Папки `backend/` и `frontend/` — части одной кодовой базы. Любое окружение (локальное, тестовое, будущий прод) разворачивается из одного и того же репозитория без форков и копий кода.

---

### Фактор 2. Зависимости

- Backend: манифест — `pom.xml`, все версии зафиксированы явно (родитель `spring-boot-starter-parent:3.3.5`, `lombok.version=1.18.42` и т.д.).
- Все Docker-образы пинятся по тегу.
- Сборка полностью изолирована в контейнере (multi-stage Dockerfile) — ничего не берётся «из системы» хост-машины.
- Frontend — vanilla JS без единой внешней библиотеки: неявных зависимостей нет физически.

---

### Фактор 3. Конфигурация

`application.yml` не содержит ни одного значения — только `${DB_URL}`, `${DB_USER}`, `${DB_PASSWORD}`, `${SERVER_PORT}`, `${FRONTEND_ORIGIN}`. Frontend — статические файлы без собственного рантайма, поэтому `API_BASE_URL` подставляется в `js/config.js` через `envsubst` при **старте контейнера** (`entrypoint.sh`), а не зашивается в код при сборке образа. Секреты и адреса — только в `.env`

---

### Фактор 4. Сторонние сервисы

PostgreSQL подключается по URL, целиком заданному конфигурацией (`DB_URL`). Замена локального контейнера БД на внешний Postgres не потребует изменений в коде — только в `.env`.

---

### Фактор 5. Сборка, релиз, запуск

- **Build**: multi-stage Dockerfile — `maven package` собирает jar в изолированном build-слое.
- **Release**: `docker-compose.yml` объединяет собранный образ с конфигурацией окружения (`.env`) и присваивает ему идентификатор — `image: notes-app-backend:${APP_VERSION:-dev}` (аналогично для frontend).
- **Run**: `docker compose up` только запускает готовый релиз, кода не меняет.

---

### Фактор 6. Процессы

Backend полностью stateless. Личность пользователя передаётся заголовком `X-User-Id` и проверяется прямым запросом к PostgreSQL на каждый вызов — состояние целиком во внешнем сервисе. 

### Фактор 7. Привязка портов

Backend сам поднимает встроенный Tomcat и биндится на `$SERVER_PORT` — без внешнего контейнера сервлетов. Frontend сам биндится на `$PORT` через `python -m http.server`. Ни один компонент не полагается на внешний веб-сервер общего назначения (nginx) — фронтенд и backend общаются напрямую по HTTP

---

### Фактор 8. Параллелизм

Можно поднять ещё какое то количество реплик бэкенда и фронтенда.

---

### Фактор 9. Утилизируемость

Состояние в БД, контейнеры быстро поднимаются и работают с данными из БД.

---

### Фактор 10. Паритет окружений

Локально через `docker-compose` поднимается тот же `postgres:16-alpine`, что предполагается использовать в любом другом окружении. Один и тот же `docker-compose up --build` работает одинаково что при первой сборке, что при повторном развёртывании

---

### Фактор 11. Логирование

Ни backend, ни frontend не пишут логи в файлы — оба пишут в stdout контейнера.

Backend пишет **структурированные логи** — одна JSON-строка на событие (встроенный форматтер Spring Boot 3.5, без сторонних библиотек: `logging.structured.format.console: ecs`).

---
