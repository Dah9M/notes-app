# Отчёт: Notes App

Домашнее задание №1 курса SRE — клиент-серверное приложение как база для последующих домашних заданий (сбор логов и метрик, деплой, балансировка трафика).

## 1. Доменная область

Приложение для ведения личных заметок (Notes App). Каждый пользователь регистрируется, входит в систему и работает со своим приватным набором заметок: создаёт, читает, редактирует и удаляет их, а также организует заметки с помощью тегов и фильтрует список по тегу. Заметки одного пользователя не видны другим пользователям.

## 2. Стек реализации

| Слой | Технологии |
|---|---|
| Backend | Java 21, Spring Boot 3.3.5 (Spring Web, Spring Data JPA), Liquibase |
| БД | PostgreSQL 16 |
| Frontend | HTML5, CSS3, vanilla JavaScript (без фреймворков и сборки) |
| Взаимодействие | HTTP/REST (JSON), фронтенд обращается к backend напрямую через `fetch` |
| Инфраструктура | Docker, Docker Compose (3 независимых контейнера: postgres, backend, frontend) |

Аутентификация реализована максимально упрощённо и осознанно: без токенов, сессий и хеширования паролей — логин/пароль сверяются напрямую в БД, а личность пользователя на последующих запросах передаётся заголовком `X-User-Id`. Это сознательное решение: задание курса SRE, а не курса по безопасности, и усложнение авторизации не добавляет ценности для последующих ДЗ (логи, метрики, балансировка), а только увеличивает объём кода. Подробности — в разделе 4 (фактор Processes).

## 3. Основные сущности

- **User** — id, username (уникальный), password, createdAt
- **Note** — id, title, content, owner (User), tags (Tag, многие-ко-многим), createdAt, updatedAt
- **Tag** — id, name (уникальный)

CRUD полностью реализован для **Note** и **Tag** (`/api/notes`, `/api/tags`). Для **User** — регистрация и вход (`/api/auth/register`, `/api/auth/login`), т.к. пользователь не является объектом самостоятельного управления в рамках предметной области приложения.

## 4. Соответствие методологии 12 факторов

| # | Фактор | Статус | Обоснование |
|---|---|---|---|
| 1 | **Codebase** | ✅ Закрыт | Один git-репозиторий (`notes-app`), папки `backend/` и `frontend/` — части одного кодбейза, деплоятся из одного источника. Множества деплоев (локальный/иные окружения) — из одной и той же кодовой базы. |
| 2 | **Dependencies** | ✅ Закрыт | Backend: все зависимости объявлены явно в `pom.xml`, версии зафиксированы через `spring-boot-starter-parent`; сборка изолирована в контейнере (`maven:3.9-eclipse-temurin-21`), ничего не берётся "из системы". Frontend: чистый vanilla JS без единой внешней библиотеки — зависимостей нет, поэтому и скрыто предполагать нечего. |
| 3 | **Config** | ✅ Закрыт | Backend получает всё из окружения (`DB_URL`, `DB_USER`, `DB_PASSWORD`, `SERVER_PORT`, `FRONTEND_ORIGIN`) — ни одного хардкода в `application.yml`. Frontend — статические файлы без собственного рантайма, поэтому конфиг (`API_BASE_URL`) подставляется в `js/config.js` через `envsubst` в момент старта контейнера (`entrypoint.sh`), а не зашивается в код при сборке образа. Один и тот же образ работает в разных окружениях без пересборки. |
| 4 | **Backing services** | ✅ Закрыт | PostgreSQL подключается по URL, целиком заданному конфигурацией (`DB_URL`). Замена локального контейнера БД на внешний managed-Postgres не потребует изменений в коде — только в `.env`. |
| 5 | **Build, release, run** | ⚠️ Частично | Docker multi-stage чётко разделяет build (`maven package`) и run (`java -jar` в `eclipse-temurin-jre-alpine`), `docker compose up --build` объединяет билд с конфигом (release) и запускает (run). Не хватает формальной стадии версионирования релизов (тегирования образов, CI/CD пайплайна) — в рамках одного студенческого проекта без выделенного CI это не реализовано; будет закрыто в следующих ДЗ курса по деплою. |
| 6 | **Processes** | ✅ Закрыт | Backend полностью stateless: нет серверных сессий, нет хранилища токенов в памяти процесса. Личность пользователя на каждый запрос передаётся заголовком `X-User-Id` и проверяется через прямой запрос к PostgreSQL (backing service), а не по локальному состоянию процесса. Любой инстанс backend может обработать любой запрос от любого залогиненного клиента — это прямое следствие того, что даже упрощённая идентификация вынесена в БД, а не в память приложения. |
| 7 | **Port binding** | ✅ Закрыт | Backend самодостаточен — Spring Boot поднимает встроенный Tomcat и сам биндится на `$SERVER_PORT`, без внешнего контейнера сервлетов. Frontend самодостаточен — `python -m http.server` сам слушает `$PORT` внутри своего контейнера. Ни один из компонентов не полагается на внешний веб-сервер общего назначения (nginx/Apache) — решение подтверждено на практике: фронтенд и backend общаются напрямую по HTTP без прослойки-прокси. |
| 8 | **Concurrency** | ⚠️ Частично | Архитектура заложена под горизонтальное масштабирование: backend stateless, вся личность пользователя проверяется через общий Postgres, поэтому несколько реплик backend могут работать параллельно за балансировщиком без расхождения состояния. На практике в рамках этого ДЗ поднят только один инстанс backend (`docker-compose.yml`) — запуск нескольких реплик и проверка распределения нагрузки между ними явно вынесены в следующее ДЗ курса ("Балансировка трафика"). |
| 9 | **Disposability** | ✅ Закрыт | Backend стартует быстро (~4 секунды по логам Spring Boot) и настроен на graceful shutdown (`server.shutdown: graceful`). Ни backend, ни frontend не пишут состояние на локальный диск контейнера — весь персистентный стейт в Postgres, поэтому оба процесса можно безопасно и быстро остановить/пересоздать в любой момент. |
| 10 | **Dev/prod parity** | ✅ Закрыт | Локально через `docker-compose` поднимается тот же `postgres:16-alpine`, что предполагается использовать в любом другом окружении — никаких заменителей вроде H2/SQLite для "упрощения" разработки. Разрыв между dev и иными окружениями минимален: тот же образ backend, тот же тип backing service. |
| 11 | **Logs** | ✅ Закрыт | Ни backend, ни frontend не пишут логи в файлы — оба пишут в stdout контейнера (подтверждено в логах: стандартный вывод Spring Boot / access-лог `http.server`). Сбор и маршрутизация логов — задача окружения выполнения (Docker/оркестратор), что и будет предметом следующего ДЗ по сбору логов. |
| 12 | **Admin processes** | ⚠️ Частично | Миграции схемы БД (Liquibase) выполняются тем же кодом и с тем же конфигом, что и сам backend — автоматически при старте приложения (подтверждено логами: применено 5 changeset'ов при первом запуске). Это удовлетворяет формальному требованию "тем же кодом и конфигом", но не идеальному варианту фактора — миграции лучше запускать отдельным одноразовым процессом, а не встраивать в старт каждого инстанса, чтобы при масштабировании backend на несколько реплик (фактор 8) миграции не пытались выполниться параллельно из каждой из них. Для одного инстанса, как сейчас, это не проблема; при переходе к нескольким репликам стоит вынести Liquibase-запуск в отдельный init-контейнер/job. |

### Итог

**9 из 12 факторов закрыты полностью**, 3 — частично, с честным обоснованием: недостающие части (версионирование релизов, фактическая проверка горизонтального масштабирования, вынесение миграций в отдельный процесс) являются предметом следующих домашних заданий курса SRE (деплой и балансировка трафика), а не архитектурными недостатками текущего решения — сама архитектура (stateless backend, конфиг через env, backing services через env, логи в stdout) уже спроектирована с расчётом на эти следующие шаги.
